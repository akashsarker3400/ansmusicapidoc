For integration engineers

Deliver to ANS Music from your own system.

Push music video releases, follow every status change with signed webhooks, and request VEVO channels — without anybody logging into a dashboard. One key, one base URL, JSON everywhere. You should be sending your first release inside an hour.

Start in 10 minutes Download OpenAPI 3.1 Request a key
REST + JSON Signed webhooks Sandbox with real events Idempotent creates No file size limit

01Overview

Everything lives under one base URL, takes and returns JSON, and answers in the same envelope every time.

Base URLhttps://server.ansmusic.io/partner
AuthenticationHeader x-api-key: ans_live_… on every request — see Authentication
Content typeapplication/json, UTF-8, on requests and responses. Files never pass through this API — see Sending files
TimestampsISO 8601 with a timezone. What you send is read that way; what we return is UTC with a Z
IdsOurs are 24-character hex strings and stable for ever. You may address a release by our id, your externalId, or the numeric videoId
VersioningThis is v1. Fields are added, never removed or renamed; a breaking change would be a new path. See the changelog

The response envelope #

Every response — success or failure — is one JSON object with the same four fields. What you want is under data; message is a sentence meant to be read, not a code to look up.

// GET /partner/me
{
  "statusCode": 200,
  "success":    true,
  "message":    "Successful",
  "data": {
    "company":       "Your Company Ltd",
    "environment":   "live",
    "scopes":        ["release:write", "release:read", "upload:write", "webhook:manage"],
    "linkedAccount": { "id": "66e7f0a1c2b3d4e5f6a7b8c9", "name": "Your Company Ltd" },
    "webhookUrl":    "https://your-system.example.com/ans/webhook"
  }
}

Lists put their page under data too — data.releases, data.channels — with the paging figures beside them. Errors keep the envelope with success: false; see Errors.

What you can do #

Upload a masterPresigned URLs straight to storage. Multipart for anything large, resumable part by part. Create a releaseTitle, artists, artwork, video, channel — idempotent on your own id. Be told what happenedApproved, sent back, rejected, ISRC issued, live — signed and retried. Answer a correctionChange what was wrong and the release returns to review on its own. Request VEVO channelsBy name. Approved on arrival when we already have it. Rehearse it allA test key sees the same API, fires the same webhooks, and reaches no store.

This version delivers music videos

Every release carries a video file and can carry a VEVO channel. Audio-only releases are not accepted through this API yet — if you need them, tell us at support@ansmusic.io and we will say when.

02Authentication

One key per environment, sent in a header. The key decides who you are, what you may do, and whether your writes are real.

  -H "x-api-key: $ANS_API_KEY"
const res = await fetch('https://server.ansmusic.io/partner/me', {
  headers: { 'x-api-key': process.env.ANS_API_KEY },
});
const { data } = await res.json();
console.log(data.company, data.environment, data.scopes);

Keys and environments #

A key is a 57-character string whose prefix names its environment, so a key pasted into the wrong config is visible on sight rather than discovered when rehearsal uploads turn up in the catalogue.

PrefixEnvironmentWhat its writes do
ans_live_…liveReal releases. They reach the review queue, the catalogue, the stores and VEVO, and are counted in royalty reports.
ans_test_…testThe same API, the same responses, the same webhooks. Nothing reaches a reviewer, a store or a report — see Sandbox.

Keys are issued only to the technical contact on file for an existing ANS Music account, and sent only to that contact. They do not expire on a timer; they are revoked by a person, on purpose. GET /partner/me tells you which environment and scopes the key you are holding has.

Scopes #

A key carries only what it needs. Tell us which of these you use and it is issued accordingly; a call outside the key's scopes is refused with 403.

ScopeAllowsEndpoints
release:writeCreate and update releases, drive the sandboxPOST /releases, PATCH /releases/:id, POST /releases/:id/simulate
release:readRead releases, statuses, ISRCs, reasonsGET /releases, GET /releases/:id
upload:writeGet upload URLsPOST /uploads, /uploads/parts, /uploads/complete
channel:writeRequest VEVO channelsPOST /channels
channel:readRead channelsGET /channels
webhook:manageSet, read and test the webhookPUT /webhook, GET /webhook, POST /webhook/test

GET /partner/me needs no scope — any valid key may ask who it is.

IP allowlist #

Tell us the addresses you call from and the key is restricted to them; a call from anywhere else is refused with 403 and a message saying so. The address checked is the one your request arrives from, so a proxy of your own is fine as long as its egress address is on the list.

Keep the key server-side

It is a bearer credential: whoever holds it is you. Never put one in a browser, a mobile app, a repository or a log line. If a key is exposed, tell us — we issue a replacement, both work while you switch, then the old one is revoked.

03Quickstart

Your first release, end to end, against a test key. Every step is one call; the whole thing takes about ten minutes.

  1. Confirm the key

    Ask who you are. This is the call to put in a health check.

    curl https://server.ansmusic.io/partner/me -H "x-api-key: $ANS_API_KEY"
# → data.environment: "test", data.scopes: [...]
  2. Point us at your webhook

    Do this before creating anything so the very first event is witnessed. The response carries a signing secret that is shown once — store it.

    curl -X PUT https://server.ansmusic.io/partner/webhook \
  -H "x-api-key: $ANS_API_KEY" -H "content-type: application/json" \
  -d '{ "url": "https://your-system.example.com/ans/webhook" }'
# → data.secret: "whsec_…"  (once, and only now)

curl -X POST https://server.ansmusic.io/partner/webhook/test -H "x-api-key: $ANS_API_KEY"
# → data.delivered: true, data.responseStatus: 200
  3. Get an upload URL and send the file

    Files go straight to storage on a presigned URL; they never pass through this API. Under 50 MB is a single PUT; anything larger is multipart — see Sending files. If you already host your media on a public URL, skip this step.

    curl -X POST https://server.ansmusic.io/partner/uploads \
  -H "x-api-key: $ANS_API_KEY" -H "content-type: application/json" \
  -d '{ "fileName": "cover.jpg", "contentType": "image/jpeg", "category": "image", "size": 1592000 }'
# → data.mode: "single", data.uploadUrl: "https://…", data.fileUrl: "https://cdn.ansmusic.io/…"

curl -X PUT "$UPLOAD_URL" -H "content-type: image/jpeg" --data-binary @cover.jpg
  4. Create the release

    Nine fields are required — title, artist, the two files, label, genre, language, description and the VEVO channel. Send your own externalId so a retry can never create it twice.

    curl -X POST https://server.ansmusic.io/partner/releases \
  -H "x-api-key: $ANS_API_KEY" -H "content-type: application/json" \
  -d '{
    "externalId":    "REL-2026-0412",
    "title":         "Akashe Batase",
    "primaryArtist": ["Nadia Rain"],
    "label":         "Sundarban Records",
    "genre":         ["Pop"],
    "language":      "Bengali",
    "description":   "Official music video.",
    "channel":       "NadiaRainVEVO",
    "releaseDate":   "2026-10-01T12:00:00Z",
    "videoUrl":      "https://cdn.ansmusic.io/uploads/videos/…mp4",
    "imageUrl":      "https://cdn.ansmusic.io/uploads/images/image/…jpg"
  }'
# → 201, data.status: "pending", data.videoId: "801142"
# your webhook receives release.created
  5. Move it, and watch the events arrive

    On a test key you play the reviewer. Each simulated status fires the same webhook a real change does.

    curl -X POST https://server.ansmusic.io/partner/releases/REL-2026-0412/simulate \
  -H "x-api-key: $ANS_API_KEY" -H "content-type: application/json" \
  -d '{ "status": "needs_fix", "reason": "Cover art is below 1400px." }'
# your webhook receives release.needs_fix, data.reason set

curl -X PATCH https://server.ansmusic.io/partner/releases/REL-2026-0412 \
  -H "x-api-key: $ANS_API_KEY" -H "content-type: application/json" \
  -d '{ "imageUrl": "https://cdn.ansmusic.io/uploads/images/image/…-fixed.jpg" }'
# → data.status: "pending" — back in review

Then go through the pre-launch checklist, send us one real release on the live key, and switch the rest across.

04Sandbox & testing

Write to support@ansmusic.io for a test key. It is the same API, the same base URL and the same responses — the only difference is where what you write ends up.

With a test key…LiveTest
Uploads reach storageYesYes
Releases are created, readable and updatable by youYesYes
Webhooks fire, signed the same wayYesYes
Rate limits applyYesYes
Appears in the ANS Music review queueYes—
Reaches the catalogue, the stores, VEVOYes—
Counted in any royalty reportYes—

Test rows are hidden at the database level rather than filtered out by each screen, so no query anywhere can accidentally include them. Nothing you do with a test key needs cleaning up, and nothing you do with it can be seen by anybody at ANS Music. The two environments are sealed from each other: a live key cannot read a test release, and vice versa — you get a 404.

Play the reviewer #

Approvals and rejections happen when a reviewer here gets to them, which is no use when you are testing a handler on a Tuesday afternoon. A test key moves its own releases — see POST /releases/:id/simulate. Each move fires the real webhook, signed with your real secret, carrying the release as it now stands.

Before you go live #

Worth having done at least once against the test key:

  • A multipart upload of something over 1 GB, with one part deliberately failed and retried.
  • A repeated POST /releases with the same externalId — confirm you get the same release back with 200 Already created rather than a second one.
  • A webhook with a deliberately wrong signature — confirm you reject it with 401.
  • A webhook replayed an hour later — confirm your timestamp check rejects it.
  • The same event id delivered twice — confirm your handler does the work once.
  • A needs_fix answered with PATCH — confirm your dashboard shows it back in review.
  • ?updatedSince= after leaving your endpoint down for a while — confirm you catch up.
  • A 429, by exceeding a limit on purpose (three webhook tests in a minute will do it) — confirm you wait for RateLimit-Reset rather than hammer.

Then send us one real release on the live key before switching the rest across.

05Sending files

Ask for a URL, put the bytes there, use the resulting fileUrl in the release. Your file never passes through our servers, so size stops mattering.

Do not POST the file to this API

Our edge refuses any request body over 100 MB, and no music video gets through that. The presigned URL is a direct route to storage; the API only signs it.

You can skip this section entirely if you host your own media on a public URL: send it as videoUrl / imageUrl in the release. Both routes are supported and always will be — but a URL you host must stay reachable until the release is delivered, and a private, expiring or IP-restricted link will fail at review.

Start an upload #

POST/partner/uploadsscope upload:write · 30/min
FieldTypeNotes
fileNamestringrequiredUsed for the extension and a readable object name. Sanitised; not used verbatim.
category"video" | "image"optionalDefault video. Decides the storage prefix and the default content type.
contentTypestringoptionalDefault video/mp4 or image/jpeg to match the category. Send the real one.
sizeintegeroptionalBytes. Decides single vs multipart. Absent is treated as large — guessing small and being wrong fails at the end of a long upload; guessing large costs one round trip.

Under 50 MB — one PUT

{
  "mode":      "single",
  "key":       "uploads/images/image/yourco-cover-a1b2c3.jpg",
  "uploadUrl": "https://…?X-Amz-Signature=…",
  "fileUrl":   "https://cdn.ansmusic.io/uploads/images/image/…"
}

Over 50 MB, or size unknown — multipart

{
  "mode":     "multipart",
  "key":      "uploads/videos/yourco-master-a1b2c3.mp4",
  "uploadId": "2~k9Vt…",
  "partSize": 10485760,
  "fileUrl":  "https://cdn.ansmusic.io/uploads/videos/…"
}

For single: PUT the bytes to uploadUrl with the same content-type you declared. For multipart: split the file into partSize chunks and continue below. Either way, fileUrl is what you put in the release — it is known before a single byte is sent. Signed URLs are valid for one hour.

Sign parts #

POST/partner/uploads/partsscope upload:write · 60/min
{ "key": "uploads/videos/…", "uploadId": "2~k9Vt…", "partNumbers": [1, 2, 3, 4, 5] }

→
{ "urls": [ { "partNumber": 1, "uploadUrl": "https://…" }, … ] }

Ask for a block at a time rather than all of them at once — a URL signed an hour before it is reached will have expired. At most 200 part numbers per request. PUT each chunk to its URL and keep the ETag response header; you will need it to finish.

Part numbers start at 1. Every part except the last must be at least 5 MB; using exactly partSize for all but the last is the simple way to satisfy that. Parts may be uploaded in parallel and in any order.

Finish the upload #

POST/partner/uploads/completescope upload:write · 30/min
{
  "key": "uploads/videos/…", "uploadId": "2~k9Vt…",
  "parts": [ { "partNumber": 1, "eTag": "\"9b2cf5…\"" }, { "partNumber": 2, "eTag": "\"e1f0a3…\"" } ]
}

→
{ "key": "uploads/videos/…", "fileUrl": "https://cdn.ansmusic.io/uploads/videos/…" }

Send every part with its ETag, in any order — we sort them, and the quotes around an ETag are stripped for you. A part that failed is retried on its own rather than the whole file; that is as much the point of parts as the size is.

A complete multipart upload #

Node.js, with parts sent five at a time and each retried on its own. This is the shape to copy; the language does not matter.

import { open } from 'node:fs/promises';

const BASE = 'https://server.ansmusic.io/partner';
const H = { 'x-api-key': process.env.ANS_API_KEY, 'content-type': 'application/json' };
const api = async (path, body) => {
  const r = await fetch(BASE + path, { method: 'POST', headers: H, body: JSON.stringify(body) });
  const j = await r.json();
  if (!j.success) throw new Error(j.message);
  return j.data;
};

export async function uploadMaster(filePath, fileName) {
  const fh = await open(filePath);
  const size = (await fh.stat()).size;

  const start = await api('/uploads', { fileName, contentType: 'video/mp4', category: 'video', size });

  if (start.mode === 'single') {
    const buf = Buffer.alloc(size); await fh.read(buf, 0, size, 0);
    await fetch(start.uploadUrl, { method: 'PUT', headers: { 'content-type': 'video/mp4' }, body: buf });
    return start.fileUrl;
  }

  const { key, uploadId, partSize } = start;
  const total = Math.ceil(size / partSize);
  const done = [];

  const putPart = async (partNumber, uploadUrl) => {
    const offset = (partNumber - 1) * partSize;
    const len = Math.min(partSize, size - offset);
    const buf = Buffer.alloc(len); await fh.read(buf, 0, len, offset);
    for (let attempt = 1; ; attempt++) {
      const r = await fetch(uploadUrl, { method: 'PUT', body: buf });
      if (r.ok) return { partNumber, eTag: r.headers.get('etag') };
      if (attempt === 3) throw new Error(`part ${partNumber} failed: ${r.status}`);
      await new Promise(res => setTimeout(res, 1000 * attempt));
    }
  };

  // Sign five at a time so a URL is always fresh when it is used.
  for (let n = 1; n <= total; n += 5) {
    const partNumbers = Array.from({ length: Math.min(5, total - n + 1) }, (_, i) => n + i);
    const { urls } = await api('/uploads/parts', { key, uploadId, partNumbers });
    done.push(...(await Promise.all(urls.map(u => putPart(u.partNumber, u.uploadUrl)))));
  }

  const finished = await api('/uploads/complete', { key, uploadId, parts: done });
  await fh.close();
  return finished.fileUrl;   // → videoUrl for POST /releases
}

Anything else in the body is ignored

Deliberately, and it is worth knowing which: status, isApproved, isTest and the rest of the review fields are ours. A release arrives pending whatever you send, and which environment it lands in comes from the key, never from the body.

Send it twice on purpose

externalId is your own id, and sending it buys you two things. A repeated call returns the release you already made — same id, 200 and the message Already created rather than 201 — instead of creating a second one. And you can address the release by your id everywhere (GET, PATCH, simulate, ?externalId=) rather than storing ours.

Without it, a retried request after a timeout creates a second release. With it, retrying is safe — including after a 500.

Release date and timezone

Give releaseDate a timezone, one of two ways — the offset in the date, or the wall clock with releaseTimezone:

{ "releaseDate": "2026-10-01T18:00:00+06:00" }
{ "releaseDate": "2026-10-01T18:00", "releaseTimezone": "Europe/London" }

An offset in the date always wins over releaseTimezone. A date with neither is read in Dhaka time (Asia/Dhaka), and the response says so in a warnings list beside the release, so a schedule meant for another clock is caught on the call that set it:

{ "id": "…", "status": "pending", …,
  "warnings": ["releaseDate \"2026-10-01T18:00\" has no timezone, so it is read as Asia/Dhaka time. Send an offset (\"2026-08-25T18:00:00+06:00\") or a releaseTimezone."] }

warnings appears only when there is something to say — a date read in Dhaka time, a version or releaseTimezone we did not recognise — and only on the response to the call, never on reads or webhooks. Nothing that carries a warning is refused.

Version

version decides what follows the title on YouTube. We add it at delivery, in the words VEVO's delivery guidelines use, so send the bare title:

version"Akashe Batase" goes out as
officialAkashe Batase (Official Video)
lyricAkashe Batase (Official Lyric Video)
audioAkashe Batase (Audio) — audio over a still image
liveAkashe Batase (Live)
interviewAkashe Batase (Interview)
behind_the_scenesAkashe Batase (Behind The Scenes)
teaserAkashe Batase (Teaser)
originalAkashe Batase — nothing added

A title that already says it — Akashe Batase (Lyric Video) — is not given a second one. Left out, nothing is added.

Common phrasings are understood too — Official Video, Lyric Video, lyrics, Official Audio, BTS, trailer. Anything else is not refused: the release is accepted, nothing is added to the title, and the response carries a warnings entry naming the value it did not recognise. A value you sent before this field existed keeps working exactly as it did.

Visibility

unlisted publishes the video on YouTube but keeps it out of search and off the channel page: only people with the link find it. public, the default, lists it everywhere.

Status lifecycle #

Six statuses. status says which; statusDetail says it in a sentence; reason carries a reviewer's words where there are any.

pendingWith us for review. Where every release starts, and where it returns after any edit.
needs_fixSent back. reason says what. Answer with PATCH and it returns to review.
approvedAccepted, on its way to the stores. The ISRC is issued at this moment if you did not send one.
deliveredDelivered to VEVO. youtubeVideoId and videoUrl follow when VEVO publishes it, with release.youtube_linked.
rejectedreason says why. Final: cannot be edited or resubmitted.
taken_downRemoved from the stores.

The ordinary path is pending → approved → delivered. A correction inserts needs_fix → pending before that, as many times as it takes. Each move is a webhook event.

We may edit what you send, and we will tell you

A description a store will not take, a genre that has to be mapped to the one that store actually has, a typo in a title — these are corrected here rather than sent back to you, because sending one back costs a release its date. Whenever a descriptive field changes you get release.updated, carrying the release as it now stands. Write it back into your catalogue: from that point ours is what the stores receive, and a difference between the two surfaces on a statement rather than as an error.

UPC

Every video gets its own barcode, sent to VEVO as the release's ICPN. It is the video's, not the audio single's: a music video is a product of its own. Send yours in upc if you have one; leave it out and we assign one from our own range when the release is approved, the same moment its ISRC is issued, and upcAssignedByAns is true.

A upc is never a reason to refuse a release. One that fails the GS1 check digit, or is already on another release, is ignored and named in warnings, and ours is assigned instead. Once a release has a UPC it cannot be changed. Releases delivered before October 2026 went without one and keep it that way.

ISRCs

Send your own if you have one; it is kept exactly and never replaced. Leave it out and we issue one from our own range when the release is approved — you get release.isrc_assigned with the code, and isrcAssignedByAns is true from then on. A code that is already in use anywhere in our catalogue is refused at creation.

07Webhooks

Set a URL once and we call you whenever anything changes — including when a reviewer here approves something, which is the case you cannot poll for usefully.

Every delivery is a POST with a JSON body, signed with a per-key secret over a timestamp and the body, in the scheme Stripe and GitHub use. Reply 2xx quickly and do the work afterwards; we retry four times over about a minute, then stop — and nothing is lost, because everything a webhook carries is also readable from the API.

The payload #

POST https://your-system.example.com/ans/webhook
content-type:    application/json

  "environment": "live",
  "sentAt":      "2026-09-15T12:41:07.512Z",
  "data":        { …the release object, or the channel object… }

FieldNotes

eventOne of the events below.

Set the webhook #

PUT/partner/webhookscope webhook:manage · 5/min
{ "url": "https://your-system.example.com/ans/webhook" }

→ 200 "Webhook set"
{
  "url":           "https://your-system.example.com/ans/webhook",
  "secret":        "whsec_9f3c…",
  "secretRotated": true,
  "note":          "Store this secret now — it is not shown again, and it is NOT your API key. …"

The URL must be https. The first call mints a signing secret and returns it once. Calling again with a different URL — correcting a typo — leaves the existing secret alone, so a verifier that is already live keeps working: secret comes back null and secretRotated: false.

To mint a new secret on purpose, send { "url": "…", "rotateSecret": true }. To remove the webhook, send { "url": "" }.

The signing secret is not your API key

They are two different credentials. The API key (ans_live_…) is what you send us. The signing secret (whsec_…) is what we sign with, and it exists only in the response to this PUT. Verifying a delivery with the API key produces a signature that never matches, on every event, with nothing to say why — which looks exactly like a webhook that is not connected.

GET/partner/webhookscope webhook:manage · 20/min
{ "url": "https://your-system.example.com/ans/webhook", "secretSet": true }

What is configured. The secret itself is never returned — only whether one exists.

Verifying signatures #

Compute HMAC-SHA256 over "<x-ans-timestamp>.<raw body>" with your signing secret, hex-encode it, prefix v1=, and compare in constant time to x-ans-signature. Use the raw request body — bytes as received — not a re-serialised object. Refuse a timestamp more than five minutes old, so a captured delivery cannot be replayed later.

import crypto from 'node:crypto';
import express from 'express';

const SECRET = process.env.ANS_WEBHOOK_SECRET;   // whsec_…  (not the API key)
const seen = new Set();                          // swap for your store

const app = express();
app.post('/ans/webhook', express.raw({ type: 'application/json' }), (req, res) => {
  const ts  = req.get('x-ans-timestamp') ?? '';
  const sig = req.get('x-ans-signature') ?? '';
  const raw = req.body;                          // Buffer — bytes as received

  const expected = 'v1=' + crypto.createHmac('sha256', SECRET).update(`${ts}.`).update(raw).digest('hex');
  const fresh = Math.abs(Date.now() / 1000 - Number(ts)) < 300;
  const valid = sig.length === expected.length && crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected));
  if (!valid || !fresh) return res.status(401).end();

  const evt = JSON.parse(raw.toString('utf8'));
  if (seen.has(evt.id)) return res.status(200).end();   // a retry — already done
  seen.add(evt.id);

  res.status(200).end();                          // answer first, work after
  setImmediate(() => handle(evt));
});

function handle({ event, data }) {
  switch (event) {
    case 'release.needs_fix':      /* show data.reason, let somebody fix it, PATCH */ break;
    case 'release.isrc_assigned':  /* write data.isrc into your catalogue */ break;
    case 'release.updated':        /* copy the descriptive fields back */ break;
    case 'release.delivered':      /* data.videoUrl is live */ break;
  }
}

Delivery, retries and catching up #

  • Timeout — 8 seconds per attempt. Answer 2xx immediately and do the work on a queue.
  • Retries — four attempts: immediately, then after 2 s, 15 s and 60 s. Any non-2xx or timeout is retried; the same id is sent each time.
  • Order — events are sent as they happen, but retries mean they can arrive out of order. Trust data.status and data.updatedAt over the sequence you received them in.
  • After an outage — GET /partner/releases?updatedSince=<when you went down> returns everything that changed. There is no replay endpoint because none is needed: every event's content is the current state of the release.
  • One URL per key — a live key and a test key each have their own webhook and their own secret.
